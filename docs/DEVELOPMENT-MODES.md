# Режими розробки TSukenya

## За замовчуванням — швидка розробка

Виконувати перевірки за змістом правки. Не запускати Docker, усі браузери та всю регресію після кожного збереження, коміту чи уточнення дизайну. Успішну перевірку повторювати лише після зміни коду, що впливає на її результат, або для розв'язання конкретного збою. Зміна документації не потребує бізнес-тестів.

| Правка | Достатня перевірка |
| --- | --- |
| Документація, інструкції, скрипти | Посилання, синтаксис, безпечний план виконання; для скрипта — відповідна поведінка |
| React / типи | Типи й lint; один сценарій зміненого компонента |
| Спільний Select / ComboBox | Відповідні історії, пошук/клавіатура/фокус, вигляд на комп'ютері й телефоні |
| Верстка | Перегляд зміненого екрана на широкому та вузькому екрані, потрібна перевірка геометрії; інші ширини при знайденому дефекті |
| API | Тести зміненого контракту, помилки й права, якщо зачеплені |
| Гроші / залишки / зарплата | Відповідні серверні сценарії; PostgreSQL-конкурентність, якщо змінено проведення або повторні запити |
| Друк | Змінений макет, переддруковий перегляд і PDF з фізичними розмірами |

Приклади з кореня репозиторію:

```sh
npm exec --workspace frontend -- tsc --noEmit
npm exec --workspace frontend -- eslint src/shared/ui/ComboBox.tsx
npm run test:components --workspace frontend -- -t 'Keyboard Selection'
npm run test --workspace frontend -- src/shared/api/client.test.ts
npm run test:visual --workspace frontend -- --project=chromium-mobile --grep 'combobox'
PYTHON_BIN=.venv/bin/python  # або шлях до вашого готового середовища
ERP_DB_PATH=/tmp/tsukenya-targeted.sqlite3 "$PYTHON_BIN" manage.py test tests.test_erp --noinput
```

Візуальна перевірка використовує вже зібраний Storybook. Після зміни компонента перед нею один раз виконати `npm run build:storybook`. Цільові серверні перевірки запускаються з ізольованими даними; прибрати `DB_HOST` та інші змінні виробничої бази з оболонки. SQLite не підтверджує конкурентність PostgreSQL.

## Перевірка функції

Після завершення сценарію перевірити пов'язані компоненти й один користувацький шлях. Спільна правка може вимагати більшого покриття, але причину розширення треба вказати. Не додавати автоматично всі інші модулі. Записати результат і невирішені обмеження в підсумку роботи.

## Повна перевірка — окрема команда

```sh
npm run test:full -- --plan  # лише перелік етапів; без тестів і контейнерів
npm run test:full           # один повний прогін, без автоматичних повторів
```

Використовувати повний режим за явним запитом користувача: «повна перевірка», «проганяй усі тести» або ця команда. Не запускати його як завершення кожної звичайної задачі. Для контрольного релізу погодити цей режим у плані релізу; якщо його вже замовлено, додаткове підтвердження не потрібне.

Команда включає перевірки React, API й синхронізації, збірки, історії Storybook та канонічні Linux PNG; всі серверні тести на тимчасовій PostgreSQL; сценарії чинного порталу, CRM, верстку Chromium/WebKit і автономний демонстраційний каталог. На першій помилці виконання зупиняється. Після виправлення повторити невдалий етап; другий повний прогін потрібен лише за конкретною причиною або новим запитом. Зразки PNG автоматично не оновлюються.

Передумови: встановлені npm-залежності, Docker, Python із `server/requirements.txt`, локальні Playwright Chromium/WebKit. `PYTHON_BIN` задає інтерпретатор, інакше використовується `.venv/bin/python` або `python3`. Підготовка браузерів — `npm exec -- playwright install chromium webkit` (Linux: додати `--with-deps`). Docker може завантажити QA-образ і PostgreSQL, якщо їх немає в кеші.

Скрипт не приймає адресу бази: видаляє успадковані змінні підключення, створює власну PostgreSQL на випадковому порту тільки `127.0.0.1` та прибирає свій контейнер і тимчасові дані. Браузерні сценарії створюють власні локальні бази. Звіт — `test-results/full-check.json`; сліди й PNG помилок — у `frontend/test-results/` та `frontend/playwright-report/`. Режим не публікує код і не змінює VPS чи Google-таблицю.

## CI

- `Frontend quick checks`: лише типи, lint, формат і API unit-тести; PR з правками frontend/залежностей і відповідні зміни в основній гілці. Попередній незавершений запуск скасовується.
- `Full quality (manual)`: тільки ручний запуск у GitHub Actions; використовує ту саму `npm run test:full`. Автоматичного повного прогону на push/PR немає.
- `Server quick checks`: повні серверні тести Django на тимчасовій SQLite (Python 3.12, як у робочому образі), перевірка, що міграції відповідають моделям, і Node-сценарії без браузера (`sync-sim`, `catalog-import-parser`, `csv-format`, `runtime-recovery`, `promotion-legacy`). Запускається для PR і основної гілки зі змінами в `server/`, `tests/`, `app/`, `manage.py`, зокрема для оновлень Python-залежностей. Близько хвилини.
- У тому ж workflow задача `postgres` запускає всі серверні тести на тимчасовому PostgreSQL 18 (той самий образ, що на сервері). Там перевіряються блокування рядків і одночасні проведення; якщо хоч один тест пропущено, задача червона.
- Чому дві бази: SQLite — швидка ізольована база для тестів, браузерних сценаріїв і локального запуску; робочий облік — лише PostgreSQL. Образ сервера має `TSUKENYA_REQUIRE_POSTGRES=1` і без `DB_HOST` не стартує, тож тихий перехід продакшену на SQLite неможливий.
- Браузерні сценарії й візуальні зразки в автоматичний CI не входять. Для змін проведення та повторних запитів вони залишаються обов'язком задачі; швидкий CI не засвідчує їх.

## Стан міграції

На 01.10.2026 `frontend/` містить React/TypeScript/Vite, спільні контролі React Aria, Storybook і основу API-клієнта. Каталог і студію цінників інтегровано в робочий портал; торговельні екрани ще не перенесені. Деталі — [CATALOG-MIGRATION.md](CATALOG-MIGRATION.md) та [LABEL-STUDIO.md](LABEL-STUDIO.md). Django/PostgreSQL лишаються сервером і джерелом облікових даних.

`app/` обслуговує чинний портал. `design/workspace.*` — демонстраційний макет, на який посилається документація і тест. Це не доведене сміття. Видаляти старий модуль після перенесення його маршрутів і сценаріїв, перевірки відсутності імпортів/викликів і перенесення потрібних регресій. Не видаляти робочу реалізацію лише через появу React-основи.
