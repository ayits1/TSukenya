# TSukenya на VPS

Стан на 01.10.2026. Адреса: <https://tsukernya.pp.ua/>; HTTPS, приватний вхід, www → основний домен. Код і Compose: `/opt/tsukenya`, проєкт `tsukenya`.

## Сервіси та дані

- `tsukenya-web-1`: Django 5.2.17 / Gunicorn, UID 10001, 2 workers / 4 threads, 768 MiB, 1 CPU. Порт 8080 доступний лише Docker-мережі; Caddy з `/opt/edge` проксіює на це унікальне ім’я. Gateway і проєкт catering не змінювалися при CRM-релізі.
- `tsukenya-tsukenya-postgres-1`: PostgreSQL 18.6, image digest зафіксований; мережа `tsukenya_accounting` internal, порт БД не публікується. Volume `tsukenya_accounting_data`, PGDATA `/var/lib/postgresql/18/data`, 1 GiB / 1 CPU.
- Застосунок підключається як `tsukenya_app`: власник тільки бази цього проєкту та її таблиць, без SUPERUSER / CREATEDB / CREATEROLE. Чинний адміністратор `tsukenya` збережений для обслуговування.
- `.env` (root, 0600): початковий hash входу, Django secret та пароль обмеженої app-ролі. `.env.database` (root, 0600): окремий сильний пароль адміністратора БД; він не передається вебконтейнеру. `.private/db-app-password` — приватний файл для повторення підготовки ролей. У Git і Docker build context секретів немає.
- `storage/legacy-migration.sqlite3`: незмінний узгоджений знімок перед переходом, UID 10001, 0400. Старий `storage/tsukenya.sqlite3` більше не використовується для запису. Не редагувати / не синхронізувати його з PostgreSQL.
- При запуску: Django migrations; одноразовий `bootstrap` із migration snapshot; далі Gunicorn. Якщо CRM вже ініціалізована, імпорт не перезаписує документи чи пароль.

## Оновлення

1. `python3 /opt/tsukenya/backup.py` — consistent PostgreSQL dump та checksum.
2. Передавати тільки код; не перезаписувати `.env`, `.env.database`, `.private`, `storage` чи DB volume.
3. У `/opt/tsukenya`: `docker compose -p tsukenya -f compose.production.yaml config --quiet`, потім `docker compose -p tsukenya -f compose.production.yaml up -d --build web`.
4. Перевірити health контейнерів і HTTPS `/health`, вхід, каталог / цінники та облікові екрани. На робочій базі не запускати Django test command: він створює / видаляє test database. Тести PostgreSQL запускаються в окремому QA-оточенні з тестовим адміністратором.
5. Для відокремлення ролей після свіжої міграції / відновлення є `deploy/separate_db_roles.py`, запускається root. Він використовує чинний захищений admin-доступ і створює обмежену роль, без виводу паролів. У новому оточенні спочатку підготувати PostgreSQL та імпортувати snapshot під адміністративним доступом, потім виконати розділення ролей і запустити production Compose.

## Копії та відновлення

`/etc/cron.d/tsukenya-backup`: щодня 03:15 UTC запускає `backup.py`. Копії `/opt/tsukenya/backups/tsukenya-crm-*.dump`, custom pg_dump format, checksum `.dump.sha256`, права 0600, каталог 0700, зберігання 14 днів. Архів перевіряється `pg_restore --list`.

Копію `tsukenya-crm-20260930T093511Z.dump` відновлено в **окрему** базу `tsukenya_restorecheck`; перевірено 53 документи, 52 товари та нуль стартових товарних / грошових проведень. Тестову базу після перевірки видалено. Копіювання повного архіву на Mac очікує окремого дозволу після відмови автоматичної перевірки безпеки. Зовнішню копію поки не створено; постійне резервування поза VPS не налаштовано.

Команди для перевірки архіву виконуються root через `docker exec` у DB-контейнері, користувач БД `tsukenya`. Відновлювати тільки у нову порожню базу / новий volume. Перед підміною робочої БД зупинити запис і зробити нову копію. `pg_dump` не містить PostgreSQL-ролей та паролів: зберігайте приватну конфігурацію окремо й повторюйте підготовку обмеженої ролі.

**Відкат до старого SQLite-сервера після появи операцій у PostgreSQL не переносить їх автоматично.** Спочатку зберегти нову БД і оцінити перенесення всіх нових документів; не запускати старий snapshot як актуальний облік. Для відкату UI / коду в межах нової CRM зберігати сумісність міграцій PostgreSQL.
