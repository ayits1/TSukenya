# Клієнтська база: B26, перший етап · 04.10.2026

## Робочий маршрут і межа міграції

`#trade/customers` монтує React/TypeScript `features/customers` із тим самим набором спільних контролів, що й каталог. Список має серверний пошук за іменем/телефоном/email, фільтр активності, сторінки по30 клієнтів та картку обраного контакту. Дані й остаточні грошові розрахунки залишаються у Django/PostgreSQL. Storybook використовує лише синтетичні контакти.

Створення/редагування контакту та історія документів поки відкривають чинні native діалоги. Перед редактором перечитується ERP snapshot: контакт, створений після старого snapshot, відкривається саме для редагування свого ID. Історія отримує авторитетне ім’я й вибраний магазин; пізня відповідь іншого маршруту не змінює нову форму. Чинна HTML-реалізація залишається fallback для релізу без React bundle. Це не міграція всього CRM.

## API та фінансові факти

- `GET /api/v1/crm/customers`: контакти, paging30, `q`, `active=yes/no`, `page`, `store`; позитивні ID, обмеження пошуку250, явні помилки параметрів.
- `GET /api/v1/crm/customers/{id}`: контакт, scope/current knowledge, покупки та борги. OpenAPI — `contracts/crm.openapi.json`; generated types — `shared/api/crm.generated.ts`. Невідомий JSON декодується під час виконання, а не лише приводиться до TypeScript типу.
- Факти включають лише проведені документи до поточної київської дати; чернетки/скасовані/майбутні виключені. PostgreSQL читає один REPEATABLE READ READ ONLY snapshot. Це поточний стан знань, не історичний as-of.
- Середній чек = сума продажів / кількість проведених чеків. Повернення показуються окремо та через net; повністю повернений чек залишається фактом покупки. Повернення прив’язане до клієнта через вихідний продаж, навіть коли його власний party порожній. Чужий магазин виключено.
- Сегменти є прозорими фактами: немає покупок / одна покупка / повторні покупки. Довільних VIP порогів немає.
- Борг повторно використовує обліковий калькулятор `obligation`, включно з оплатами, авансами, розподілом і поверненнями. Строк раніше сьогодні — прострочений; сьогодні — ще ні; зіпсовані старі строки показано як документи з невідомою датою. Prefetch batch200 обмежує пам’ять; необмеженого SLA для історії не заявлено.
- Гроші — Decimal strings на API; відображення великих сум зберігає копійки без float округлення.

## Права, кеш і взаємодія

Контакти — спільний довідник відповідно до чинної ERP policy. Власник, менеджер, бухгалтер і касир мають читання; складська роль — ні. Фінансові факти обмежені доступними магазинами. Касиру API повертає `debt:null` і `canEdit:false`; редагування доступне іншим переліченим ролям відповідно до чинного редактора.

TanStack Query розділяє ключі списку/профілю/магазину; запити мають AbortSignal. Ручне оновлення та remount після підтвердженого native запису прибирають застарілі дані, не повторюючи POST. Фільтри й обраний контакт збережені при поверненні на маршрут. Legacy `tsukenya:data-changed` без domain оновлює кеш; scoped domains без customers його не чіпають. Окреме міжпристроєве CRM polling ще не реалізовано.

Після вибору фокус переходить у заголовок картки, після закриття історії — на кнопку історії. Повернення до списку фокусує вибраний контакт або пошук, якщо контакт відсутній у поточних результатах. Помилка читання перед редактором видима й сфокусована; вона не відкриває порожню форму створення.

## Цільові докази

Вісім різних сценаріїв PostgreSQL пройшли інкрементально: покупки/повернення/скасування, облікові оплати/аванс/строки, ролі/магазини, paging/нові/неактивні контакти, помилки, RR READ ONLY/query budget100 документів, виключення майбутніх документів та HTTP історія source-linked повернення. Unit API перевіряє runtime decoding/decimal money/дати/paging/abort. Типи, змінений lint, production build та п’ять Storybook станів пройшли.

`tests/customers-ui.cjs` відкриває справжній маршрут на власній тимчасовій SQLite та Chrome:66 контактів,30/30/6 paging, продажі50/повернення10/середній25, історія, клавіатура/фокус, актуальне редагування контакту, помилка GET/retry, підтверджений запис без дублю. Геометрія1440/320 та axe — PASS. Команда: `PYTHON_BIN=/path/to/python npm run test:customers:ui`. Артефакти можна зберегти через `QA_CUSTOMERS_ARTIFACT_DIR`. Не підключати production DB або спільну Sheet.

Після інтеграції перевірено лише зачеплені native сценарії: empty/search, confirmed-write/GET-only recovery, late users/detail GET після переходу на нову чернетку. Повна регресія, VPS, Google Sheet, реальний телефон/скринрідер не запускалися.

## Що залишається у B26

Задачі контакту/воронка, згода на повідомлення та журнал лояльності залишаються наступними етапами. Для балів потрібні правила власника: база, курс, строк дії, списання, межі й повернення. Провайдер повідомлень також не обраний. Немає вигаданих балів або автоматичних розсилок; B26 загалом не позначено завершеним.
