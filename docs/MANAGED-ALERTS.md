# Керована робота зі сповіщеннями (B19)

## Облікова умова й робота

У системних задачах нестача/термін/борг (`tasks/auto_*`) `_alertActive` означає стан облікової умови. Робота має незалежний `_alertWorkState`: `open`, `accepted`, `deferred`, `completed`, `resolved`. Публічний `status` зберігає сумісність: todo/doing/done. «Виконано» завершує роботу, але не приховує активну нестачу чи борг: рядок і лічильник активних умов залишають їх видимими. Незмінний cron не відкриває виконану роботу наново й не змінює ревізію задачі. Усунення умови позначає resolved; повторна поява відкриває новий `_alertCycle` у тому самому ID. Ручні задачі не входять у цей процес.

«Прийняти» фіксує автора й час, «Відкласти» — явну дату повернення та непорожню причину, «Виконано» — автора й час завершення. Повернення до роботи є окремою дією. Прикладові межі реалізації не є новим розпорядженням власника щодо термінів роботи.

Дата відкладення — дата повернення, а не останній відкладений день. Має бути пізнішою за поточну київську дату. У перший cron у цю дату або пізніше задача повертається в open один раз; GET ніколи не пробуджує задачу й не пише аудит. Подія пробудження зберігає попередню дату, причину, цикл і джерело перевірки.

Передрук `tasks/reprint_*` використовує ті самі дії. Незмінне читання ціни не відкриває завершений передрук. Новий фактичний `PriceChange` скидає прийняття/відкладення, створює наступний цикл того самого рядка, зберігаючи `_priceChange`, товар та ERP-контекст магазину. Переходи B14 та облікові ціни не змінені.

## API й права

`POST /api/erp/alerts/tasks/<auto_ID|reprint_ID>/actions`:

```json
{"action":"defer","revision":"opaque","idempotencyKey":"UUID","until":"2026-10-10","reason":"Очікуємо поставку"}
```

Дії: accept/defer/complete/resume. `until` доступне лише defer; reason обов’язкова для defer й має до 500 символів. Authoritative поточний стан і revision приходять у `task: {id, revision, data}`; `replayed`, `appliedRevision`, `appliedCycle` розрізняють точне підтвердження попередньої дії та поточний стан після наступних змін.

Власник/керівник використовують чинну авторизацію задач, зокрема scope магазину та окремий фінансовий доступ. Авторизація повторюється перед кожним новим запитом і точним повтором. Чужий автор, задача або зміст під тим самим UUID — 409 idempotency_conflict; стара ревізія — 409 revision_conflict. Канонічний JSON/HMAC робить ревізію незалежною від порядку ключів PostgreSQL JSONB. Квитанції `AlertTaskAction` — окрема модель (0014_managed_alerts після 0013_idea_projects), не прихований реєстр у settings. Точний повтор не створює нового аудиту й не перезаписує пізнішу роботу/новий цикл.

Старий status-only PATCH сумісний: сервер оновлює work state/автора й прибирає відкладення, якщо статус змінено. Клієнт не може підробляти системні поля або видаляти системні задачі. `/api/state` передає окрему task revision.

## Поріг придатності SKU

`Product.expiryAlertDays` і create/patch: nullable integer 0..3650. Null/порожнє поле зберігає чинний типовий поріг **7 днів**; явний 0 — повідомлення у день придатності. Прострочені ненульові партії включаються завжди. Це SKU-поріг у картці товару, без нової ієрархії магазинних правил. Поріг не змінює строк самої партії, придатність для продажу чи собівартість. Валідація працює на v1 та legacy; API/редактор/порівняння конфлікту мають той самий контракт. Хибне попереднє legacy значення читається як типовий поріг без запису виправлення в GET.

## Клієнт і розклад

Відкладення містить календар, причину, явне підтвердження, повідомлення з фокусом та захист незбереженого введення при Escape. Невизначена відповідь повторює незмінний перший UUID/body. Якщо після цього введено нову дату/причину, повтор підтверджує першу дію й залишає нові поля чернеткою для окремого збереження. Intent живе протягом поточної сторінки, без обіцянки відновлення після reload. Помилка оновлення списку після підтвердженої дії пропонує повторити лише GET. Native runtime має окремий `TSUKENYA_REFRESH_AFTER_WRITE` бар’єр: будь-яке попереднє читання завершується перед новим GET.

Збережено зовнішній cron кожні 30 хв і попередження stale90 хв; нового планувальника або бізнесового розкладу немає. Контроль/дії працюють під одним ledger_lock.

## Цільова перевірка

`tests/test_managed_alerts.py`: lifecycle/відкладення/права/ревізії/точні повтори/SKU-пороги/GET/передрук/PG-конкурентність. Пов’язані `test_alert_lifecycle`, `test_task_scope` перевіряють metadata ownership та чинний контроль. `tests/runtime-managed-refresh.cjs` перевіряє бар’єр попереднього GET для зовнішнього підтвердженого запису. `tests/managed-alerts-ui.cjs` — приватний локальний Django/SQLite, keyboard/lost-response/нове введення/Escape/320px/44px/цикл. `QA_ALERTS_FROM=read` у цьому browser-тесті окремо перевіряє підтверджений POST, помилку наступного GET і повтор лише читання без нового POST/квитанції. Storybook `ExpiryThresholdIsExplicit` перевіряє, що дробовий поріг лишається чернеткою, а 0 записується як 0. Повної регресії, зовнішніх мутацій чи розгортання ці перевірки не виконують.
