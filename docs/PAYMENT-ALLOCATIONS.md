# Платежі, аванси й управлінська звірка — B15

## Реалізований сценарій

У «Торгівля → Фінанси» платіж містить суму, магазин, контрагента, рахунок і явні розподіли по документах. Один платіж 1 600 грн може закрити A на 1 000 грн і B на 500 грн; залишок 100 грн стає невикористаним авансом. Платіж створює один `CashEntry`, незалежно від кількості розподілів.

У блоці авансів користувач створює «Використання авансу» або «Повернення авансу». Використання зменшує борги без повторного руху коштів. Повернення робить один протилежний грошовий рух тільки в межах невикористаної суми. Пошук вихідних документів відкриває окреме вікно, зберігає чернетку й повертає фокус після Escape.

Звірка з вибраним контрагентом показує початкове/кінцеве сальдо, операції, сторно, борги, невикористані аванси та вікові групи. Сальдо кожного рядка розраховане через усю попередню історію, включно з попередніми сторінками. Операції видаються по 30 рядків. Історичні аванси додані до вкладки «Залишки на дату» та її CSV.

## Implementation defaults

Ці правила є явними технічними defaults реалізації; їх не слід називати погодженими бізнес-рішеннями власника.

- Розподіл лише явний: немає автоматичного FIFO за боргами, взаємозаліку або оплати майбутнього документа залишком авансу.
- Один платіж має одного контрагента, один магазин і один напрям. Покупець/постачальник — різні напрями; контрагентський аванс відокремлений від `payroll_payment`.
- Джерела розподілу — проведені `sale`, `receipt`, `debt_opening` з відповідним напрямом. До 200 різних документів на одну операцію; нові суми розподілів — десяткові рядки, строго до копійок.
- Дата розподілу не раніша за дати платежу й боргового документа; повернення авансу не раніше платежу. Закритий період діє як для інших документів.
- Новий нерозподілений аванс не створюється для неактивного контрагента; оплата старого боргу, використання й повернення існуючого авансу дозволені.
- Повернення оплаченого товару залишається `customer_return`/`supplier_return` і власними правилами повернення коштів. Воно не повертає невикористаний аванс і не збільшує його автоматично.
- Додатне сальдо звірки означає «нам винні», від’ємне — «ми винні». Борг документа й аванс показані окремо; тільки контрольна формула звіряє їх зі сальдо.
- Строки оплат залишаються чинними реквізитами боргових документів. Немає вигаданого строку для старих документів; «Без строку» — окрема група. Чинний список боргів має фільтр строку/прострочення для календаря оплат. Політика обов’язкових кредитних строків не нав’язана новою функцією.

## Модель й API

`PaymentAllocation` пов’язує `settlement` (платіж або використання авансу), початковий `payment`, борговий `source` та `amount`. Пара `(settlement, source)` унікальна; сума додатна. Чернетка платежу видаляється зі своїми розподілами. `payment` використовує `RESTRICT`, щоб власний розподіл платежу не блокував каскадне видалення цієї ж чернетки; незалежні використання авансу захищені. Боргове джерело має `PROTECT`.

### POST /api/erp/vouchers

```json
{
  "kind": "payment",
  "date": "2026-10-04",
  "store": 1,
  "party": 2,
  "account": 3,
  "amount": "1600.00",
  "idempotency_key": "stable-client-uuid",
  "allocations": [
    {"source": 101, "amount": "1000.00"},
    {"source": 102, "amount": "500.00"}
  ]
}
```

`advance_allocation` використовує `reference` початкового платежу, суму та `allocations`; сума повинна точно дорівнювати сумі розподілів. `payment_refund` використовує `reference`, `account`, суму; розподілів не має. Решта CRUD/post/reverse/revision/idempotency/CSRF/audit контракту ваучерів збережена.

Детальний DTO платежу/використання додає `allocations[{source,number,amount}]`; проведений платіж також має `unallocated`. Компактний вибір боргів користується чинним `/api/erp/references?purpose=payment`, тому бухгалтер не потребує доступу до мутацій або собівартості надходжень/продажів.

### GET /api/erp/advances

Фільтри: `store`, `party`, `id` (ID платежу), `direction=customer|supplier`, `q` (номер/контрагент), `from`, `to`, `page`. Відповідь:

- `items[{payment,number,date,store,party,party_name,direction,total,unallocated}]`;
- `total`, `page`, `pages`, сторінка 30, запит за межами діапазону обмежується останньою;
- `totals{customer,supplier}` для всіх авансів після фільтра, не тільки сторінки.

### GET /api/erp/party-statement

`party` обов’язковий; `store`, `from`, `to`, `page` опційні. За замовчуванням поточний місяць до сьогодні. Відповідь:

- `opening_balance`, `closing_balance`, `debit`, `credit`;
- `items[{voucher,number,kind,date,store,amount,reversal,allocations,balance}]`, `total/page/pages`;
- `debts`, `advances`, `debt_total`, `advance_total`, `age`;
- `reconciliation{net_documents_and_advances,matches}`, `basis=accounting_dates`.

Гроші в нових DTO — десяткові рядки. Для покупця контрольне сальдо = борги − аванси; для постачальника = −борги + аванси. `advance_allocation` має нульову зміну сальдо й явні розподіли, а не новий платіж.

## Авторитетність і історія

`settlements.py` є спільним адаптером для `obligation`, вибору документів, поточних боргів, історичних залишків, звірки та перевірки регістрів. Для розподілу на дату мають бути чинні всі три документи: подія розподілу, платіж і боргове джерело. Сторно — в київській даті `reversed_at`; це історія за обліковими датами, не «що було відомо користувачу тоді».

Проведення використовує наявний глобальний `LedgerLock` в атомарній транзакції: два одночасні списання одного авансу не можуть витратити більше його залишку. Повтор post не додає розподіли/рухи. Збереження й проведення 65 джерел використовують пакетні запити без запиту боргу для кожного джерела.

Скасування боргового джерела блокується активним розподілом; скасування платежу — активним використанням/поверненням. Спершу скасовуються залежні операції. `reconcile` додатково перевіряє суми, напрям/магазин/дати зв’язків, чинність джерел і перевитрату авансу.

Самостійний HTTP-запит звірки працює в read-only PostgreSQL REPEATABLE READ snapshot, як B17. Менеджер/бухгалтер обмежені своїм магазином; касир і складський користувач одержують 403. Персональні зарплатні документи до цих DTO не потрапляють. Помилка GET прибирає застарілі дії/результат, а повтор запиту читає дані заново.

## Міграція і сумісність

`0009_payment_allocations` залежить від реальної `0008_promotion_campaigns`. Backfill додає один точний розподіл до кожного legacy payment з single reference, включно з чернетками/скасованими; не змінює дати, статуси, посилання чи CashEntry. Для старих прямих модельних записів без backfill адаптер читає single reference без подвійного підрахунку.

Старий клієнт із `payment.reference` працює як точна оплата одного документа. Відсутність `allocations` у PUT існуючої multi-чернетки зберігає її розподіли; явний `[]` очищає їх у аванс. Новий клієнт для multi-оплати передає `reference=null` й явні розподіли. Зарплатні аванси та складські алгоритми не змінювались.

## Перевірено

14 нових цільових серверних сценаріїв підтверджені послідовними вузькими прогонами; успішні сценарії повторювались тільки після зміни відповідного коду. Зокрема: дві оплати/один CashEntry; обидва напрями; часткове повернення товару; використання/повернення/сторно; legacy revision і видалення чернетки; CSRF/ролі/магазин; API retry; Decimal/Unicode/дублікати; історична активність трьох документів; closed period; пошкоджений refund scope; 65 джерел без N+1; 65 рядків звірки й вікові групи. На PostgreSQL18 підтверджені міграція, API й конкурентне використання/повернення; конкурентний сценарій повторений після зміни пакетного валідатора.

Окремо пройшли 7 чинних релевантних сценаріїв legacy оплат/повернень, batch browsing, фінансових боргів, історичного cut-off і reconcile. `makemigrations --check --dry-run`: no changes. `git diff --check`: чисто.

```sh
# Лише відповідний набір при зміні платежів; тестові DB_* — тільки ізольована БД.
python manage.py test tests.test_payment_allocations --noinput
# Конкурентність підтверджується PostgreSQL, а не SQLite.
python manage.py test tests.test_payment_allocations.PaymentConcurrencyTests --noinput
PYTHON_BIN=/path/to/isolated/python node tests/payments-ui.cjs
PYTHON_BIN=/path/to/isolated/python node tests/payments-ui.cjs --failure-only
```

Реальний браузер на ізольованій тимчасовій SQLite: 1 600 → 1 000 + 500 → аванс 100 → розподіл 50 без CashEntry → повернення 50 → звірка із сальдо 0. Перевірено Escape/фокус/збереження чернетки, 1440/390/320 px, історичний блок авансів; окремо — GET503 і повтор читання без застарілих дій. Повна регресія й продакшн не запускались.

## Межі

Управлінська звірка не є автоматично підписаним бухгалтерським актом чи фіскальним документом. Валюта — чинна гривня; різні напрями/магазини не згортаються. Розрахунок eligible авансів пакетний, але сканує відфільтровану історію для правильного total; для дуже великих історій потрібна окрема SQL-оптимізація із збереженням того ж адаптера. Фізичний друк акту/підпис/розсилання не реалізовані цією зміною.

Інтеграційне рев’ю додало перевірку напряму джерела в `reconcile`: sale для покупця, receipt для постачальника або debt_opening. Пошкоджені JSON-реквізити боргу/повернення дають issue з ID документа, а не зупиняють інші перевірки. Пов’язані 3 PostgreSQL-сценарії (старі malformed payloads, cash direction та нове неправильне джерело) — PASS.
