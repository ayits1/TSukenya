# Пункт 0.1: пропозиція щодо зовнішніх бекапів

04.10.2026. **Пропозиція виконавця; не прийняте рішення власника.** Чинне відкладення до після 10.10.2026 зберігається. Замовлення сховища, зміна VPS, розклад або передавання даних не виконані.

## Поточний стан за документацією

Локальний PostgreSQL custom dump щодня03:15UTC, checksum і pg_restore --list, права0600,14днів у /opt/tsukenya/backups. Це опис docs/SERVER-DEPLOYMENT.md, а не новий доказ справності cron/останньої копії: цього разу VPS не перевірявся. Копії на тому самому сервері не забезпечують відновлення після втрати всього VPS.

## Рекомендована схема

- Залишити локальні14днів для швидкого відкату.
- Додати окремий Hetzner Storage Box та restic через SFTP. Сховище відокремлене від робочого диска; додатковий незалежний від провайдера архів можна зберігати на комп’ютері власника.
- Передавати лише завершений узгоджений pg_dump із checksum. Зашифрованою копією охопити потрібні файли застосунку/вкладення та конфігурацію відновлення; codeSHA і Compose допоможуть вибрати сумісну версію коду. Копіювання живого PGDATA не замінює dump.
- Початкова запропонована ротація:30щоденних,8щотижневих,6щомісячних. Це вибір для погодження, не чинний розклад. Ємність/вартість обираються після виміру розміру та приросту даних.
- Окремі SSH credentials тільки цього backup-каталогу. Пароль restic зберегти у менеджері паролів власника й приватному файлі автоматизації; не покладатися тільки на VPS і не включати ключ від шифрування у сам зашифрований архів. Адміністративний доступ до snapshot сховища не передавати застосунку. SFTP-доступ сам по собі не є незмінним сховищем.
- Стан зовнішньої копії: останній успіх, checksum, повідомлення про збій/прострочення. Успішний pg_restore --list не дорівнює перевіреному відновленню всього застосунку.

## Перевірка перед прийняттям

1. Із зовнішньої копії відновити окрему PostgreSQL, без підключення mutation-тестів до production/спільної Sheet.
2. Перевірити міграції, бізнесові записи/залишки та read-only reconcile; виконати один ізольований сценарій після відновлення.
3. Зафіксувати витрачений час і доказ, які дані відновилися. До цього RTO не обіцяється.
4. Щоденний розклад означає потенційну втрату змін приблизно до24годин за відсутності збоїв. Перед робочою фазою власник визначає допустиму втрату; за потреби частіших копій/PITR це окремий пакет.

Для запуску потрібні вибір/активація сховища власником та команда на виконання0.1. Решта GitHub-плану продовжується незалежно.
