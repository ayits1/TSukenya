# Замовлення, резерви та виконання (B10)

## Правила

Проведене замовлення погоджено. Стан `partial`/`fulfilled` походить від кількостей проведених продажів або надходжень за незмінним `reference_line`. Окремий `OrderControl` зберігає закриття, очікувану дату поставки та версію дій. Закриття не переписує проведення й історію; невикористаний резерв звільняється, нове виконання недоступне. Сторноване замовлення скасоване.

Резерв покупця явно займає конкретні придатні партії FEFO. Він не створює документів, складських рухів чи рухів коштів. Дата `expires_on` включно діє до початку наступного календарного дня у `Europe/Kyiv`, з урахуванням DST. Партія має бути придатною до цього дня; сервер не скорочує строк. Інтерфейс показує вільну кількість та максимальну дату, достатню для всього нерезервованого залишку рядка. Для меншої кількості допустима пізніша дата, якщо є відповідні придатні партії.

Продаж за цим вихідним замовленням використовує його резерв першим, потім вільні партії; резерв належить замовленню, а не працівнику продажу. Звичайний продаж, виробництво, списання, переміщення, інвентаризація, повернення постачальнику та сторно надходження не можуть зменшити фізичний залишок нижче чужого чинного резерву. Потрібне явне звільнення. Собівартість і остання копійка рахуються один раз для сумарної витрати з кожної партії.

Сторно виконання відновлює використаний резерв тільки для відкритого замовлення з чинним строком. Після закриття або строку ця частина зберігається в історії як звільнена. Попередні залежності повернень та інших проведень продовжують блокувати передчасне сторно.

Постачальницьке замовлення має необов’язкові `expected_date` та `minimum_order_amount` (десятковий рядок, до двох знаків). Мінімум перевіряється під час погодження тільки якщо явно заданий. Історія й старі замовлення не отримують вигаданих мінімумів.

## API та доступ

- `GET /api/erp/orders/{id}` — актуальний RR/READ ONLY стан; `page` сторінки історії по 50 записів. Підсумки чинного резерву охоплюють усі записи.
- `GET /api/erp/orders/{id}?purpose=reserve` — також ліміти придатних вільних партій для кожного рядка; лише для тих, хто керує резервом.
- `POST /api/erp/orders/{id}` — `action`, додатний цілий `revision`, канонічний UUID `idempotencyKey`. Дії `reserve` (`expires_on`, `lines:[{line,quantity}]`), `release` (`reservation`, `quantity`, обов’язкова `reason`), `expire`, `close` (обов’язкова `reason`), `expected_date` (дата або порожня для очищення).
- Кількості — десяткові рядки до трьох знаків. Невідомі поля та підміна рядка/резерву відхиляються. Історія не видаляється.
- Власник та керівник керують дозволеним магазином; склад — тільки замовленням постачальнику; касир — тільки власним замовленням покупця. Читання вихідного замовлення й звичайне виконання зберігають чинний доступ ролі/магазину.
- Роль, магазин і активність повторно перевіряються після спільного ledger lock. Однаковий ключ/актор/запит повертає початковий результат без нового запису або аудиту, навіть після наступних змін. Інший зміст із цим ключем — 409. Застаріла версія — `order_revision_conflict`, 409.
- Нова форма виконання передає перевірений `payload.order_revision`; він перевіряється при Save та Post. Старі API-клієнти без цього поля зберігають чинну перевірку актуального вихідного документа.
- `StockReservation`, `ReservationUse`, `OrderOperation` не містять грошей. Міграція `0011_order_reservations` залежить від B16 `0010_monthly_budgets`.

## Цільова перевірка

`manage.py test tests.test_order_reservations --noinput` на окремій PostgreSQL: FEFO/COGS, залишок джерела, expiry/сторно, guards усіх витрат, ідемпотентність, конкурентний продаж/резерв, ролі/CSRF/магазин, RR при паралельній зміні, 56 записів історії.

`QA_ORDER_RESERVES_ONLY=1 PYTHON_BIN=... node tests/ui-audit.cjs` створює ізольовану SQLite і перевіряє реальні форми: 320/1440 px, клавіатуру/повернення фокуса, втрачений результат POST та однаковий повтор, 409 зі збереженою чернеткою, частковий продаж/звільнення/закриття, явні умови постачальника.

Після ручного розв’язання конфліктів із B16/B18 root перевірив 4 PostgreSQL сценарії: guards чужого резерву та сторно надходження, відновлення/звільнення при сторно виконання, єдине округлення собівартості власної/вільної кількості однієї партії, збережений аудит місячного бюджету. Усі PASS. Один native browser шлях після інтеграції підтвердив форми резерву/виконання й людський whitelist-аудит на 1440/320 px; старі успішні не пов’язані сценарії не повторювались. Новий сценарій зареєстровано в явній `test:full`, без запуску повної регресії.

Рев’ю відхиляє `expires_on=9999-12-31` до запису: неможливо обчислити наступний день для включного строку. Це технічна межа календаря, не додатковий бізнесовий строк резервування.

SQLite CI виявив лише різне написання `SUM` кількостей (`6`/`6.000`). Шість відповідних сценаріїв виправлено для точного Decimal-порівняння зі збереженою перевіркою типу string та максимуму трьох знаків; цільовий повтор SQLite — PASS. Серверні розрахунки й контракт до трьох знаків не змінено, успішний PG-прогін через це локально не повторювали.
