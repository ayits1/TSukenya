# Стек для розвитку TSukenya · 01.10.2026

Статус: каталог і конструктор перенесено на React/TypeScript/Vite та інтегровано в чинний портал. Storybook документує контролі, каталог і студію цінників. Сервер — Django 5.2.17 / PostgreSQL 18; API каталогу та цінників має версію `/api/v1/` та OpenAPI-контракт. Django REST Framework ще не доданий. Облікові екрани залишаються на HTML/CSS/JavaScript; наступна межа — торговельні модулі. Деталі — [CATALOG-MIGRATION.md](CATALOG-MIGRATION.md) та [LABEL-STUDIO.md](LABEL-STUDIO.md).

## Рішення

| Частина | Ціль | Причина |
|---|---|---|
| Сервер | Django, модулі за бізнес-процесами | Зберегти атомарні проведення, ролі, аудит і чинні облікові правила; окремі модулі каталогу, складу, продажів, фінансів і команди |
| База | PostgreSQL | Єдине джерело облікових даних; транзакції, обмеження та журнал руху |
| Інтерфейс | React + TypeScript + Vite | Спільні компоненти, явний стан форм/макета та перевірка типів між модулями |
| API | Поступово Django REST Framework, версія `/api/v1/`, OpenAPI | Єдині правила валідації та контракт для типізованого клієнта; облікова логіка залишається в серверних сервісах |
| Перевірки | Серверні сценарії + Storybook/Vitest + Playwright/axe + візуальні зразки | Виявляти зміни сум, залишків, прав, фокусу й компонування; типізація не перевіряє геометрію CSS |
| Розгортання | Поточний VPS, Docker Compose, Caddy | Узгоджені релізи, health, резервні копії й відкат коду |

Архітектура — один модульний застосунок: модулі мають зрозумілі межі, а проведення товарів і грошей виконуються в одній транзакційній системі. Поділ на окремі сервіси має спиратися на виміряне навантаження або потребу незалежного розгортання. Кількість товарів сама по собі не є підставою такого поділу.

## Перехід

1. **Контракт і спільні компоненти.** Зафіксувати API каталогу й макета, формати грошей/кількостей, версії макета, помилки, ролі та пагінацію. Додати типи клієнта з OpenAPI і бібліотеку контролів з перевіреними станами. Грошові суми обробляються серверним Decimal; клієнт не стає джерелом остаточних проведень.
2. **Каталог та конструктор.** Перенести їх на React/TypeScript у чинному порталі. Спочатку каталог і редагування, потім макет, вибір товару/копій і переддруковий перегляд. Зберегти фізичні розміри, чинні макети, імпорт та URL. Порівняти друк і PDF до та після переходу.
3. **CRM за модулями.** Закупівлі/склад, продажі/каса, фінанси, команда/зарплата, звіти. Кожен етап проходить регресії на окремій базі, розгортається окремим релізом і має відкат. Поточний та новий інтерфейси використовують ті самі серверні правила.

Для великих каталогів API має виконувати пошук, фільтри й пагінацію на сервері. Поточне завантаження всього каталогу в браузер — окреме обмеження, яке перехід на React сам по собі не усуває. У списках потрібні межі результатів або віртуалізація. Імпорт, інтеграції й звіти, що перевищують нормальний час HTTP-запиту, надалі слід винести в фонові завдання із повторенням та ідемпотентністю.

## Джерела

- [Django: версії та підтримка](https://www.djangoproject.com/download/) — 5.2 LTS має розширену підтримку до квітня 2028; оновлення безпеки виконуються окремими релізами.
- [React: додавання до чинного проєкту](https://react.dev/learn/add-react-to-an-existing-project) — можливий поступовий перехід окремих ділянок інтерфейсу.
- [TypeScript Handbook](https://www.typescriptlang.org/docs/handbook/intro.html) — перевірка типів до виконання програми.
- [Vite](https://vite.dev/guide/) — збірка й середовище розробки; є React/TypeScript-шаблон.
- [Django REST Framework](https://www.django-rest-framework.org/) — інструменти побудови API Django.

Це вибір архітектури за поточними вимогами, а не результат навантажувального тесту. Перед розширенням кількості магазинів/каси потрібно визначити їхню кількість і очікувані одночасні операції, перевірити конкурентні проведення та виміряти час відповіді.
