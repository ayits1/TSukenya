# Відновлення після збою оновлення даних

## Виправлена помилка

Раніше `server/runtime.js: mutate` отримував успішний запис від Django, потім виконував `await refresh()`. Збій цього GET відхиляв увесь promise як невдале збереження. Форма залишала введену назву; повторний `collection.add()` відправляв новий POST, а сервер створював інший документ. Успішний запис і читання після нього тепер мають окремі результати.

## Контракт адаптера

| Подія / виклик | Результат |
| --- | --- |
| Write HTTP / transport error | Promise відхиляється; автоматичного повтору запису немає |
| Write 200 з підтвердженим JSON, наступний GET падає | Повертається підтверджений результат запису; UI повідомляє про окремий збій оновлення |
| `TSUKENYA_REFRESH()` падає | Promise відхиляється; останній валідний cache, роль, CSRF і revisions зберігаються |
| `tsukenya:refresh-failed` | `detail={message}` з одним загальним українським повідомленням; без response body, URL сервера, stack чи приватних реквізитів |
| `tsukenya:refresh-succeeded` | Надсилається після кожного успішного GET, включно з незміненими даними; прибирає notice |
| Роль змінена при незмінених даних | Snapshot subscribers повідомляються, щоб правила навігації та UI не залишались старими |
| GET уже виконується, коли запис підтверджено | Write чекає на нього й на новий GET, запущений після відповіді запису; збережений документ видно, щойно promise запису виконано |
| `TSUKENYA_REFRESH()` під час фонового опитування | Опитування не використовується як відповідь: після нього виконується окреме читання (записи каталогу, імпорту, цін ідуть через інші API); паралельні явні виклики ділять його |
| Відмова запису 4xx з `error` | `error.serverMessage` містить українську причину сервера (права, штрихкод, 409); 5xx, не-JSON і transport помилки його не мають, UI показує власний текст |
| `update/set/delete(value, {revision})` | `If-Match` дорівнює версії, з якої почалося редагування (редактор товару); без опції — останній отриманий revision для негайних дій. Snapshot товарів і `settings/main` має `revision` |

Глобальний notice з кнопкою повтору міститься поза `#main`, щоб render сторінки його не видалив. Кнопка викликає тільки `TSUKENYA_REFRESH()`; вона не повторює POST/PATCH/PUT/DELETE. Відсутність банера була б неповним застосуванням цього контракту: користувач має знати, що показаний стан ще не оновлено.

Перед заміною cache адаптер перевіряє object `data`, string `csrf`, відому серверну `role`, а за наявності — string `labelRevision`. Некоректний payload не може автоматично надати роль owner чи стерти валідний cache. Це мінімальний decoder оболонки; поглиблена валідація окремих колекцій лишається окремим контрактом.

`collection.add()` використовує POST із серверним ID. Для `tasks`, `ideas`, `expenses` передає `Idempotency-Key`; форма явно закріплює його за початковим наміром створення. Ролі, scope задач, If-Match продукту/макета та серверні validators не змінені. Snapshot дані та `permissions()` клонуються; підписка на cached snapshot сама не виконує запитів.

## Ідемпотентне створення задач, ідей та статей бюджету (B06)

`POST /api/tasks`, `/api/ideas`, `/api/expenses` приймає заголовок `Idempotency-Key` (16–80 символів: літери ASCII, цифри, `_`, `-`). Ключ належить одній дії, колекції та автору. Під спільним `ledger_lock` сервер атомарно створює документ і `LegacyCreateReceipt`; це окрема таблиця, не запис у `settings`. Міграція — `0006_legacy_create_receipt`.

Квитанція містить ID документа, автора, fingerprint початкового JSON і створених після перевірки даних. Порядок JSON-ключів не впливає на fingerprint; `order` і зміст запиту впливають. Перевірки актуальної ролі, початкового scope та доступу до наявної задачі виконуються при кожному повторі.

| Повтор | Відповідь / дія |
| --- | --- |
| Той самий автор, key та payload; документ незмінений | 200 `{ok:true,id,replayed:true}` із первісним ID; без нового write чи audit |
| Інший payload за тим самим key | 409 `create_payload_conflict`; документ не змінено |
| Інша колекція або автор | 409 `create_key_conflict`; первісний ID не розкривається |
| Документ уже змінено після створення | 409 `create_changed` із відомим ID; жодного перезапису або автоматичного прийняття редактором |
| Документ видалено | 409 `create_deleted`; повтор не відновлює його. Legacy DELETE позначає tombstone, навіть якщо ID потім використано заново |
| Права / scope стали недоступні | Відмова доступу; квитанція не обходить авторизацію |

Native форми поточної/розвиткової задачі, ідеї, статті витрат та дія «Створити задачу» з ідеї закріплюють immutable payload (включно з `order`) і ключ за відкритою чернеткою. Автоматичний повтор `unavailable` та ручне повторне натискання використовують саме цей намір. Відмова 4xx після попереднього неоднозначного результату не прибирає ключ.

Якщо після втрати відповіді введено інший текст, наступне натискання спочатку підтверджує первісне створення. Нове введення залишається; повідомлення прямо пояснює, що для нього потрібне окреме натискання. Після підтвердженого exact retry незмінене введення очищається. `create_changed` / `create_deleted` залишають введення, виконують лише GET для актуального списку та не відпускають старий ключ; явне очищення поля назви починає нову чернетку. Звичайна перевірочна відмова першої спроби без попередньої неоднозначності дозволяє виправити введення.

Runtime `collection.add(value, {createKey})` дозволяє передати цей ключ явно. Без опції для тих самих трьох колекцій адаптер тримає ключ та копію payload за тим самим JS-об’єктом до підтвердження; новий об’єкт — новий намір. Успішний JSON має підтвердити `ok:true` та коректний `id`; зіпсована відповідь не очищає намір.

**Межа збереження:** ключ і введення живуть у відкритій сторінці. Render та повтори їх зберігають; перезавантаження браузера не відновлює чернетку. Перехід з незавершеної форми потребує явного відкидання; за неоднозначного результату повідомлення пояснює, що запис міг уже створитися. Відкидання закінчує цей намір. Серверні квитанції та tombstone зберігаються в базі.

Контракт сумісності: POST без ключа та legacy PUT продовжують працювати для старих інтеграцій; сам PUT не став ідемпотентним create. Для інших колекцій ця правка не усуває неоднозначність запису. Каталог, торговельні документи та макет мають свої контракти версій/повторів.

## Цільова перевірка

```sh
node tests/runtime-recovery.cjs
```

Pure VM без мережі й бази — PASS:

- POST успішний, GET503: один POST, підтверджений document ID повернуто, generic event надіслано.
- Explicit retry робить тільки GET; після отримання запису snapshot оновлено й recovery event надіслано.
- Реальні HTTP403 і transport помилки запису відхиляються; автоматичного повтору POST немає.
- Невдалий/некоректний GET зберігає cached snapshot, роль, permissions, CSRF і product/label revisions.
- Cashier permissions не отримують write доступ після read failure; role-only зміна повідомляє subscribers.
- PATCH/PUT/DELETE підтверджуються незалежно від наступного read failure.
- Незмінений успішний GET очищає notice; паралельні refresh callers ділять один GET.
- GET, що почався до запису, не завершує запис: після нього виконується свіжий GET; poll під час post-write GET його ділить. Явний refresh під час poll чекає на нове читання.
- 409/403 дають `serverMessage`; 503 і HTML-відповідь — ні. Редактор надсилає revision відкриття, а не новіший з опитування.

Ізольований browser helper `PYTHON_BIN=/tmp/tsukenya-crm-venv/bin/python node tests/runtime-recovery-ui.cjs` — PASS: справжній task POST200 і наступний GET503 очищають підтверджену чернетку; рівно один запис у БД та один POST. Банер зберігається на 1440/390/320 px без overflow (320 PNG переглянуто). Невдалий Enter retry сфокусував alert; успішний Enter retry виконав лише GET, прибрав банер, показав задачу й повернув фокус до заголовка. Справжня write503 залишає чернетку й не створює запис.

Після першого проходу виправлено тільки тестовий locator назви задачі (він не враховував вкладений контекст мережі); повтор `QA_RUNTIME_FROM=read` завершив read/write tail без повторення вже успішної геометрії. Helper доданий до майбутньої явної повної перевірки; повної регресії та серверних бухгалтерських тестів цього разу не запускали.


Browser працює зі справжнім isolated Django: поточні й розвиткові задачі, ідеї, статті бюджету, idea→task, автоматичний unavailable retry, відмова після нього та ручний повтор, нове введення після uncertainty, зміна/видалення збереженого запису іншим запитом. PostgreSQL тести підтверджують один документ і audit при чотирьох одночасних exact retries та відмову від заміни payload при двох різних одночасних create за одним ключем.
