# Кілька касових змін працівника за день · B04

Дата перевірки: 04.10.2026. Вихідний код: `9c04dad2b48ac59b1b544ec44e4857e273147de6`.

## Правило

Для різних касових змін одного дня працівник має окремі записи табеля.
Повторна пара «працівник × дата × касова зміна» заборонена. Без касової зміни
залишається один запис працівника за день зі ставкою та нульовим відсотком.
Кількість змін (`units`) множить лише ставку; не множить відсоток від виторгу.

Погоджене правило відсотка збережено: кожен працівник отримує власний
відсоток від усього виторгу касової зміни. Одна касова зміна, що перетинає
північ, може мати ненульовий відсоток цього працівника лише в одному його
записі. Інший день цієї ж касової зміни може містити лише ставку.
Існуючі записи, історичні дублікати й розрахунки не переписуються.

Індивідуальні ставки та відсотки фіксуються в табелі. Після нарахування
запис не редагується; зміна умов працівника не змінює старі умови. Нові
розрахунки зарплати додатково фіксують номер касової зміни поряд із ID
табеля; старі розрахунки читаються без цього нового поля. Ці зв'язки також
дозволені в whitelist бізнес-аудиту.

## Контракт і повтори

`POST /api/erp/work-shifts` додатково приймає необов'язковий
`idempotency_key` — UUID нового запису. Форма створює його один раз на
відкриту чернетку. Точний повтор повертає початковий `{id}` без нового запису
чи аудиту, навіть після подальшого редагування табеля. Інший зміст або автор
із тим самим ключем отримує `409 idempotency_conflict`. Для оновлення
залишаються ID і чинна ревізія; застаріла форма отримує `409 revision_conflict`.
Повтор природної пари без того самого ключа отримує `409 work_shift_exists`
з ID існуючого табеля. Старий API без ключа лишається доступним.

Після ledger lock сервер перечитує активність користувача, роль і магазин
перед новим записом або поверненням квитанції. Доступ мають власник і
бухгалтер у межах своїх магазинів. Створення, квитанція й аудит атомарні;
нарахування далі використовує чинні блокування й перевірки payroll.

Міграція `0016_multiple_daily_work_shifts` додає дві partial unique
constraints та `WorkShiftCreateReceipt`. У цьому ізольованому пакеті її
тимчасова залежність — `0014_managed_alerts`; під час інтеграції вона має
залежати від `0015_state_versions`. Міграція не містить перетворення даних.

## Перевірка

12 різних цільових Django тестів PASS на PostgreSQL 18, Django 5.2.17:

- Дві касові зміни одного дня, окремі ставки/відсотки/units, фактичні
  складські надходження та продажі; зарплата `525.00` (110 + 415), незмінні
  старі умови після зміни ставки працівника, джерела в розрахунку й аудиті.
- Унікальність linked/unlinked записів на рівні API та бази; ревізія другого
  запису не перезаписує перший або новіші умови.
- Точний повтор після редагування, змінений зміст, інший автор, відкликана
  роль/активність/магазин; відмови без записів і нового аудиту.
- Конкурентне створення для різних касових змін; точні повтори без дубля;
  однаковий природний запис із різними ключами; cross-midnight бонус один раз.
- Два конкурентні payroll не можуть нарахувати ті самі два записи двічі;
  повтор проведення зберігає результат. Чинні legacy duplicate-bonus та
  stale-timesheet сценарії також PASS.
