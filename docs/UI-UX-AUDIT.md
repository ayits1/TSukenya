# Аудит інтерфейсу TSukenya

## Обсяг і поточний стан

Аудит триває. Перелік нижче відділяє оглянуті екрани від ще не перевірених сценаріїв. Це не сертифікація всіх станів застосунку.

Перший ізольований браузерний прохід: 16 маршрутів, 18 форм документів, вхід та обліковий запис, ширини 1440 і 390 px — 72 знімки. Використано тимчасову SQLite, синтетичних контрагентів, працівника, надходження і продаж; виробнича база та спільна таблиця не використовувалися. На цих станах не знайдено горизонтального переповнення, помилок JavaScript чи порушень перевірених правил axe WCAG A/AA. Автоматична перевірка не оцінює правильність бізнес-сценарію й не замінює ручний огляд.

Після виправлень зібрано 100 станів: додатково форми магазину, складу, рахунку, контрагента, працівника, табеля, відкриття/закриття каси, рецептури, користувачів, облікового періоду, ПРРО та журналу. Перевірена геометрія не показала переповнень чи кнопок менших за 44 px, axe — порушень перевірених правил, браузер — помилок JavaScript. Збір продовжувався з успішних результатів після уточнення двох селекторів тестового сценарію.

## Команди й відтворення

```sh
PYTHON_BIN=/path/to/prepared/python QA_NATIVE_ONLY=1 node tests/ui-audit.cjs
PYTHON_BIN=/path/to/prepared/python QA_UX_ONLY=1 node tests/ui-audit.cjs
PYTHON_BIN=/path/to/prepared/python QA_BROWSE_ONLY=1 node tests/ui-audit.cjs
PYTHON_BIN=/path/to/prepared/python QA_SHIFT_BROWSE_ONLY=1 node tests/ui-audit.cjs
PYTHON_BIN=/path/to/prepared/python QA_OUTPUT_DIR=/tmp/tsukenya-ui-audit node tests/ui-audit.cjs
```

На macOS сценарій використовує встановлений Google Chrome; `CHROME_PATH` дозволяє явно задати інший виконуваний файл. На інших платформах потрібен Chromium Playwright. Сценарій видаляє успадковані змінні PostgreSQL, створює окрему SQLite та видаляє її після завершення. Повна регресія не запускається цими командами.

## Наступне покриття

- Форми довідників, рецептур, каси, користувачів, закриття періоду та ПРРО: додаткові стани із довгими значеннями й помилками на 320 px; базовий огляд 390/1440 вже виконано.
- Матриця ролей і магазинів, зокрема оплата доступного боргу бухгалтером; перевіряти через ізольовані дані, а не лише приховані кнопки.
- Інтегровані імпорт/Google-таблиця/масова зміна цін; конфлікти версій, часткові невдачі, повторення, порожні й великі набори.
- Всі етапи студії з вибором товару, акцією, старою ціною, довгими назвами, великим PDF; фізичний друк окремо.
- Пагінація допоміжних списків: поточні обмежені вибірки не можна видавати за всі документи/зміни. Потрібен серверний контракт повного перегляду і пошуку.
- WebKit, масштаб 200%, forced colors і ручний скринридер для змінених взаємодій.

## Документи, ролі й історія змін · 03.10.2026

Виправлено недоступність старих вихідних документів: пошук за номером/контрагентом, дати, сторінки, явні стани помилки/повторення. Окремий дочірній dialog не перебудовує чернетку. Підписи джерел повернення показують суму продажу; залишок боргу — тільки для оплати. Попередження про недоступне джерело та кнопка очищення оновлюються разом із вибором.

Історія касових змін/табеля завантажується сторінками й зберігає фільтри після запису. Відкрита каса лишається доступною за межами останніх 100 історичних записів. Старий табель завантажується за ID; касова зміна — за магазином і датою. Вибір зарплатних змін зберігається між сторінками; список вибраних доступний окремо.

Докази: 65 джерел/3 сторінки, 64 документи історії клієнта, пошук найстарішого номера, фокус/клавіатура/повторення, реальний scoped бухгалтер із частковою оплатою надходження; 130 касових/520 робочих змін, старий ID поза state, ширини 1440/390/320, вибір каси поза сторінкою, збереження табеля й фільтрів, зарплатний вибір між сторінками та захист від пізньої відповіді. Серверні тести перевіряють доступ/дати/eligibility/порожні сторінки, приховування cost і звіти дозволених магазинів. Один пов’язаний торговельний сценарій підтвердив зарплату 401,00 грн, залишки й кошти.

Розширені грошові та облікові правила залишаються пропозиціями в BUSINESS-IMPROVEMENTS.md. Невиправлені допоміжні обмеження: ledger/journal pagination, великі боргові списки, решта ролей у legacy задачах та імпорт/конфлікти; наступний прохід зосередиться на них.

Додатковий scoped cashier-прохід підтвердив API/UI cost redaction, підпис повністю оплаченого джерела повернення 20,00 грн, очищення/фокус та відновлення недоступної reference-чернетки. Єдиний повтор стосувався тестового очікування канонічної кількості `1.000`; повторено лише новий recovery-хвіст. Після релізу перевірено живі допоміжні списки, пошук, Escape/фокус і порожній табель без mutation-запитів. Артефакти на поточній машині: `/tmp/tsukenya-live-document-search-{1440,390,320}.png`.

Окремо підтверджено ще один дефект бюджету: `settings.stores` у Django може бути масивом назв магазинів, тоді як бюджет підставляє його у numeric input. Через це поле кількості порожнє; запис числа в той самий ключ перезаписує список. Потрібно узгодити каталог магазинів та плановий параметр бюджету без зміни реальних магазинів. Це лишається відкритим для наступної хвилі.
