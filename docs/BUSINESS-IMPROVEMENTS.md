# Бізнес-логіка TSukenya: аудит і план розвитку

## Межі та доказовість

Аудит спирається на поточні моделі, серверні сервіси, маршрути API, клієнтські сценарії та тексти тестів у робочому дереві. Переглянуто каталог, цінники, закупівлі, склад, виробництво, продажі, касу, фінанси, зарплату, клієнтів, задачі, бюджет, звіти, права та імпорт/синхронізацію. Робоча база, приватні облікові дані й Google-таблиця для цього аудиту не відкривались. Первинний аналіз не змінював бізнес-код. Наступна хвиля закриває конкретні UI/API дефекти B01 і B27 та частину B24; цільові ізольовані перевірки наведено нижче й у UI-UX-AUDIT.md. Повну регресію не запускали.

Позначення доказів:

- **Реалізовано** — конкретне правило є у перевіреному коді. Це не твердження про результат нового тестового прогону чи налаштування VPS.
- **Підтверджена прогалина** — у конкретному шляху API або моделі відсутній необхідний контроль; наведено сценарій наслідку. Ізольований тест потрібен перед виправленням.
- **Обмеження** — свідомо спрощена модель, описана у коді або [CRM-IMPLEMENTATION.md](CRM-IMPLEMENTATION.md).
- **Пропозиція** — наступний функціонал; не видається за наявний.

Пріоритети: **P0** — контроль доступу або захист облікових даних; **P1** — коректність щоденних торговельних операцій; **P2** — повнота процесів і масштабування; **P3** — наступні можливості після базових правил. Рекомендована черговість усередині пріоритету наведена наприкінці.

## 2. Першочергові прогалини

### B01 · P0 · Єдина політика видимості собівартості

**Стан 03.10.2026:** витік собівартості касиру через DTO документа виправлено: обов’язковий користувач у `voucher_json`, вилучення cost/value на сервері в усіх відповідях; UI не показує недоступну суму як нуль. Цільові серверні тести перевіряють GET/POST/PUT/post; reverse для касира лишається забороненим. Розширена матриця можливостей читання — окрема пропозиція.

**Доказ:** `catalog.py: serialize` повертає касиру `cost=None`, `markup=None`; `/api/erp/stock` у `views.py` видаляє `value`. Водночас `reporting.py: voucher_json` безумовно повертає `cost` документа, `cost` товарних рядків та `value` складських рухів. GET деталей продажу доступний касиру через `permission(user, 'sale')`. Отже, приховану в каталозі собівартість можна отримати через інший дозволений маршрут.

**Пропозиція:** один серверний набір можливостей читання: вартість запасу, собівартість, персональна зарплата, фінансові залишки. Передавати користувача/політику у всі DTO, включно з відповідями створення, проведення і повернення. UI не має бути місцем, де захищається поле.

**Залежності:** затверджена матриця ролей; узгодження полів із клієнтом. **Приймання:** для касира заборонені суми відсутні у списку, деталях, POST/PUT/post/reverse відповідях та експорті; для власника/дозволених ролей збережені. Перевірка на ізольованому документі, що має ненульову собівартість.

### B02 · P0 · Задачі та спільні налаштування мають дотримуватись scope

**Доказ:** `views.py: legacy_state` для задач/ідей перевіряє лише `scope != 'operations'`, але не `data.store`. `legacy_mutation` дозволяє менеджеру `col=='tasks'` без перевірки магазину чи простору задачі. `alerts.py: sync_alerts` створює задачі з `store`. Відомий ID дає менеджеру технічний шлях змінити задачу іншого магазину або розвитку, попри приховану навігацію. Також `legacy_state` повертає `settings/main` цілком усім ролям, а не дозволений набір налаштувань.

**Пропозиція:** окремий серверний DTO задач; явні правила мережевих задач без магазину; перевірка і поточного, і нового scope/store при зміні. Формувати налаштування за allowlist для ролі: реквізити цінника відділити від фінансових/інтеграційних налаштувань.

**Приймання:** менеджер магазину A не бачить/не змінює задачу B чи розвитку за прямим ID, не може перевести задачу у чужий магазин; власник бачить мережу; автоматичні задачі лишаються в правильному магазині. Не припускати, що всі поля налаштувань уже містять секрети: їх чутливість треба визначити за схемою.

### B03 · P1 · Заборонити безконтрольну зміну одиниці обліку

**Доказ:** `catalog.py: save_product` і `views.py: legacy_mutation` дозволяють змінювати `unit` використаного товару. Захист посилань є для видалення, але не для одиниці. `StockLot.quantity` не перераховується, а `reporting.py: stock` підписує наявний залишок поточною `product.data['unit']`. Зміна «шт» на «кг» перепідписує старі кількості, тоді як рядки проведених документів мають попередню одиницю.

**Пропозиція:** базова одиниця товару незмінна після першого облікового використання. Для іншої фасовки — окремий SKU або одиниці продажу з явно збереженим коефіцієнтом перерахунку. Перетворення існуючих залишків — окремий контрольований документ, якщо воно справді потрібне.

**Приймання:** обидва API каталогу та імпорт відхиляють зміну використаної базової одиниці; редагування назви/метаданих працює; невикористаний товар можна виправити. Історичні документи й поточний залишок мають узгоджені одиниці.

### B04 · P1 · Одна зарплатна база на участь у касовій зміні

**Доказ:** `models.py: WorkShift` унікальний лише за `(employee, date)`. `views.py: work_shift_save` дозволяє дату між відкриттям і закриттям касової зміни. Якщо касова зміна перетнула північ, один працівник може мати записи на обидва дні з тією самою `cash_shift`. `services.py: payroll_amount` у кожному записі бере весь виторг `shift=s.cash_shift`, незалежно від дати запису. Це створює шлях двічі врахувати один оборот.

**Пропозиція:** окремий запис участі працівника в касовій зміні з однією відсотковою базою; оплачувані одиниці/частки ставки — окреме поле. Для поточної моделі мінімальний захист — контроль повтору `(employee, cash_shift)` при ненульовому відсотку. Додатково визначити правило кількох працівників: кожен отримує власний відсоток від усього виторгу чи є спільний відсотковий фонд. Наявний код робить перше; це не можна мовчки замінити другим.

**Приймання:** зміна через північ не дублює бонус одного працівника; кілька змін одного дня підтримуються цільовою моделлю; зміна умов завтра не переписує минулий розрахунок. Приклад: 500 грн ставка + 3% від 10 000 грн = 800 грн за одну участь.

### B05 · P1 · Повернення після нарахування зарплати

**Доказ:** `post_voucher`/`reverse_voucher` блокують продаж/повернення, якщо є `WorkShift` цього магазину з `date__gte=v.date` та проведеною зарплатою. `payroll_amount` віднімає повернення за продажами касової зміни до дати нарахування. Випадок повернення наступного дня після нарахування не переобчислює минулий бонус; а зарплата за поточний/пізніший день може блокувати таке повернення. Правило залежить від дат табеля, а не лише від конкретного зарплатного знімка.

**Пропозиція:** зафіксувати бізнес-правило: бонус за чистий оборот на момент закриття зміни, або коригування бонусу в наступному періоді. У другому варіанті додати документ зарплатного коригування з посиланням на повернення; минулий знімок не переписувати. Звичайне дозволене повернення не має вимагати скасування всієї пізнішої зарплати магазину.

**Приймання:** продаж D1, нарахування D1, повернення D3 і нарахування D3 дають визначений, пояснений результат; повтор коригування не дублює суму; виплата/аванс залишаються окремими рухами. **Залежність:** B04 і погоджене правило компенсації бонусу.

### B06 · P1 · Конфлікти чернеток і точна ідемпотентність

**Доказ:** `save_voucher` блокує регістр, але PUT чернетки не має revision. Дві послідовні записи зі старих форм перезаписують одна одну. Повторний `idempotency_key` перевіряє лише тип документа і scope, повертаючи попередній документ навіть із відмінними рядками/сумою. `entity_save`, `work_shift_save` також не мають revision. Каталог і макет уже мають такий захист.

**Пропозиція:** revision для чернеток/табеля/довідників; відповідь 409 із поточним станом та збереженням локальної форми. Ключ створення пов’язати з користувачем, типом і відбитком нормалізованого запиту: повтор того самого запиту повертає результат, інший зміст із тим самим ключем — конфлікт. Це не замінює атомарну блокаду проведення.

**Приймання:** два пристрої не можуть непомітно втратити рядки; повтор після обриву мережі не створює другий документ; повтор того самого ключа з іншою сумою відхиляється; конфлікт показує, що змінилось. **Залежність:** версійний контракт CRM.

### B07 · P1 · Підтверджена ціна і повноваження на знижку в продажу

**Доказ:** `services.py: save_voucher` приймає довільну додатну ціну `sale`/`customer_order`, не порівнює її з каталогом та не зберігає причину відхилення. `app/erp.js: retailPrice` підставляє поточну ціну, але клієнтська підстановка не обмежує прямий API-запит. Це підтримує ручну ціну, однак не має меж знижки за ролями.

**Пропозиція:** серверний знімок базової й акційної ціни, фактичної ціни та джерела відхилення. Правила: дозволена знижка касира, погодження менеджера, причина продажу нижче собівартості, строк дії спеціальної ціни. Зміна каталогу до проведення потребує явного підтвердження нового розрахунку або зафіксованої ціни замовлення.

**Приймання:** касир не обходить ліміт прямим API; погоджена знижка записується з автором/причиною; історичний чек не змінюється при редагуванні каталогу; акційна ціна в каталозі, продажу і ціннику збігається. **Залежність:** матриця повноважень і правила ціноутворення.

## 3. Повнота щоденних процесів

### B08 · P1 · Звірка касової різниці та повернення готівки

**Доказ:** `views.py: shift_action` зберігає `expected_cash`, `counted_cash`, примітку й аудит, але не створює коригуючого `CashEntry`. Наступна зміна відкривається за обліковим `cash_balance`, а не за порахованою готівкою. Для `customer_return`, `expense`, `payroll_payment`, `payment` готівковий рух не проходить ту саму вимогу відкритої зміни, що готівковий `sale`.

**Пропозиція:** розбіжність → задача звірки → підтверджена нестача/надлишок окремим документом; не списувати автоматично без причини. Визначити, які рухи каси вимагають відкритої зміни, і позначати їх `shift`, включно з поверненням. Підсумки зміни мають пояснювати кожен вхід/вихід, інкасацію та різницю.

**Приймання:** очікувано 1 000, пораховано 990 → 10 грн у реєстрі нез’ясованих різниць; після підтвердженого списання баланс 990; наступна зміна починається з узгодженої суми. Повернення готівки показує касу/зміну й автора.

### B09 · P1 · Активність учасників перевіряти при проведенні

**Доказ:** `save_voucher` перевіряє активність магазину й контрагента; для працівника перевіряє магазин, але не `active`. `post_voucher` повторно перевіряє магазин, не активність контрагента/працівника. `shift_action` перевіряє магазин працівника, але не активність. UI фільтрує активних у частині форм, що не є серверним правилом.

**Пропозиція:** матриця дозволених операцій з неактивними записами. Новий продаж/замовлення/відкриття зміни — лише активним; повернення, погашення боргу та виплата вже нарахованої зарплати колишньому працівнику мають лишитись можливими. Перевіряти обрану політику також перед проведенням старої чернетки.

**Приймання:** деактивація між збереженням і проведенням не обходить правило; історичні документи доступні; старий борг дозволено закрити. Не застосовувати blanket-заборону до всіх дій неактивного учасника.

### B10 · P2 · Замовлення, резерв і виконання

**Доказ:** `purchase_order`/`customer_order` мають документні рядки без складського руху; `validate_reference_quantities` контролює виконання, але `StockLot` не має резерву; це прямо зазначено в CRM-документації.

**Пропозиція:** життєвий цикл замовлення: чернетка, погоджено, частково виконано, виконано, закрито/скасовано. Окремі резерви з терміном і власником, часткове звільнення, доступно = придатний залишок − резерв. Мінімум постачальника, очікувана дата і невиконаний залишок для закупівлі.

**Приймання:** резерв не змінює фінансову собівартість; конкурентні резерв/продаж не перевищують запас; частковий продаж зменшує свій резерв; строк вивільняє лише невикористану частину; документ відображає залишок виконання. **Залежність:** визначений пріоритет касового продажу щодо резерву.

### B11 · P2 · Кілька партій одного товару в надходженні

**Доказ:** `save_voucher` вимагає унікальний product у рядках; `reference_line` підбирається першим рядком за товаром; `supplier_return` підбирає перший вхідний рух товару. Поточне спрощення змушує розбивати одну накладну постачальника на кілька надходжень.

**Пропозиція:** явна ідентичність рядка замовлення/партії. Дозволити кілька рядків SKU з різними партіями/термінами; повертати конкретні отримані партії; додаткові витрати розподіляти по всіх рядках із точним залишком копійок.

**Приймання:** одна накладна з двома строками одного SKU має один борг і правильний FEFO; часткове повернення не бере довільну першу партію. **Залежність:** нові рядкові ID у API, B06; міграція збережених посилань.

### B12 · P2 · Виробництво: версії рецепта, вихід і придатність

**Доказ:** `post_voucher` гілка `production` використовує `payload.recipe` або поточний `product.data.recipe`; зберігає `consumed`. Вхідні компоненти перевіряються на придатність, але строк вихідної партії не перевіряється щодо компонентів і технологічного правила. Рецепт має лише інгредієнт/кількість, без версії, нормативних втрат, пакування, витрат праці/виробництва.

**Пропозиція:** версія рецепта зі знімком у документі, нормативний/фактичний вихід, технологічні втрати, собівартість упаковки та явно дозволені додаткові витрати. Строк виходу визначати за правилом продукту/технології, а не універсально прирівнювати до найкоротшого строку інгредієнта. Простежуваність від готової партії до конкретних компонентів.

**Приймання:** редагування рецепта не змінює проведену партію; використані партії доступні в деталях; сума списань і дозволених витрат дорівнює вартості виходу; невалідний строк блокується за затвердженим правилом. **Залежність:** B11, правила рецептур реального асортименту.

### B13 · P2 · Асортимент і мінімум за складом

**Доказ:** `reporting.py: stock` застосовує `product.data.minStock` до кожного складу; для кожного складу перебирає всі товари. Немає складського асортименту/мінімумів. `alerts.py` використовує ці підсумки: товар із мінімумом створює контроль навіть у складі, де ним не торгують. Товари з нульовим залишком і історією рухів, але без мінімуму, не потрапляють у totals: стартовий запит бере лише `quantity__gt=0`, fallback додає лише `minimum>0`, попри коментар про історію рухів.

**Пропозиція:** таблиця SKU × склад: активність, мінімум, ціль, термін доставки, постачальник; окрема фільтрація «нульові з історією». Задача поповнення лише для активного асортименту; показати відмінність «немає обліку», «нуль», «лише прострочене», «зарезервовано».

**Приймання:** кавовий товар не вимагає запасу на некавовому складі; проданий до нуля товар доступний у звірці/експорті; приховані SKU з реальним залишком не зникають із бухгалтерського контролю.

### B14 · P2 · Правила акцій і історія цін

**Доказ:** `catalog.py` зберігає regular/promotionPrice і прапорець promotion, але немає періоду дії, області магазину, автора погодження чи повної історії цін. `AuditEvent` для каталогу записує метод/контракт, без попередньої/нової ціни. `priceAt` — дата перевірки поточної ціни, а не журнал усіх змін.

**Пропозиція:** кампанія з початком/кінцем, магазинами, SKU, правилом ціни і пріоритетом конфлікту; сервер визначає чинність. Окремий журнал ціни: до/після, джерело, автор, причина; завдання передруку після зміни. Дата перевірки лишається окремою.

**Приймання:** закінчення акції відновлює звичайну ціну на сервері; перекриття двох акцій має однозначний результат; старий цінник видно як неактуальний; продаж і друк використовують одну чинну ціну. **Залежність:** B07, часова зона й політика магазинних цін.

### B15 · P2 · Борги, аванси і звірка з контрагентом

**Доказ:** `obligation` рахує залишок за конкретним документом; `payment` не дозволяє суму понад цей борг. Початковий борг підтримано. Немає авансу постачальнику/клієнтського депозиту чи розподілу однієї банківської оплати між кількома документами. Нарахована зарплата й аванс працівника мають окрему модель, її не слід переносити на контрагентів без правил.

**Пропозиція:** платіж і його розподіли, невикористаний аванс, акт управлінської звірки, календар оплат, вікові групи боргу; повернення грошей із посиланням на платіж. Строк оплати — обов’язковий для продажу в борг/умов кредиту за політикою.

**Приймання:** 1 500 грн платежу покриває 1 000 грн документа A і 500 грн B без дублю руху коштів; залишок авансу переноситься; повтор API не розподіляє вдруге. **Залежність:** B06, B17.

## 4. Звіти, бюджет і управління

### B16 · P1 · Чітко відділити бюджетну модель від фактичної беззбитковості

**Стан 03.10.2026:** виправлено технічний конфлікт кількості/назв магазинів (`budgetStores`), точні суми й відновлення autosave; нуль/від’ємна маржа має чесний стан. Формула лишається орієнтиром за каталогом. Облік план/факт за місяцем/магазином та зважена модель продажів ще не реалізовані.

**Доказ:** `app/portal.js: totals` бере просту середню маржу по товарах із cost>0 та price>0, ділить суму fixed+variable на цю маржу. Це не зважена структура продажів, а variable у legacy expenses є місячними сумами, не ставкою на одиницю виторгу. В інтерфейсі вже є пояснення про модель каталогу й coverage — його зберегти.

**Пропозиція:** назва «Орієнтир за каталогом» для існуючого розрахунку; фактична маржа за проведеними продажами/поверненнями окремо. Бюджет: місяць, магазин, стаття, план; фактичні expense зі спільним ID статті, відхилення; змінні витрати як явні суми або відсоток від бази. Для кожного показника показувати період, покриття, формулу й неповні дані.

**Приймання:** дві різні структури продажів за тим самим каталогом дають різну фактичну модель; нуль/від’ємна маржа не відображає вигадану точку беззбитковості; бюджет не створює CashEntry. **Залежність:** довідник статей і B17.

### B17 · P1 · Звіти «за період» і «станом на дату»

**Доказ:** `reporting.py: report` фільтрує обороти за from/to, проте debtqs бере всі проведені борги без граничної дати, а `obligation` враховує всі поточні оплати/повернення. Отже, борги у звіті за минулий місяць є поточними. by_store має лише виторг/валовий прибуток; операційний результат по магазинах не деталізований. Поточні `StockLot` не є історичним знімком залишку.

**Пропозиція:** явні вкладки/контракти «Обороти періоду» та «Залишки на дату». В останньому — борг/товар/кошти лише за рухами до cut-off; алгоритм скасувань має узгоджуватись із датою сторнування. Фактичні витрати й зарплату показати по магазинах/статтях; мережеві витрати розподіляти лише за збереженою політикою.

**Приймання:** оплата у листопаді не змінює борг станом на 31 жовтня; звіт без cut-off прямо підписаний «Поточні борги»; сума магазинів і мережевих нерозподілених витрат сходиться з результатом мережі. **Залежність:** B15, визначення облікової дати скасування.

### B18 · P2 · Бізнес-аудит і розшифровки показників

**Доказ:** `AuditEvent.detail` є JSON; `draft_saved` записує лише kind, `entity_saved` — name, `legacy_changed` — метод; список аудиту обрізаний останніми 200 без пагінації. У зарплаті calculation уже має хороший знімок; фінансові звіти повертають агрегати без джерельних документів.

**Пропозиція:** події із нормалізованими до/після дозволених бізнес-полів, причиною, actor, request_id, revision; фільтрована пагінація. Для звітного показника — розшифровка документів/рядків і формула. Паролі, сесії та персональні секрети не включати у diff.

**Приймання:** зміна ставки/ціни/бюджету має автора і старе/нове значення; операційний результат можна відтворити з розшифровок; роль не отримує заборонені персональні поля через журнал. **Залежність:** B01/B02, версійний контракт.

### B19 · P2 · Автоматичні задачі як керований процес

**Доказ:** `alerts.py: sync_alerts` створює задачі за ключем умови й закриває усунені; повтор зберігає status активної задачі. Користувач може позначити активну умову done, і повторний контроль лишить done, хоча умова ще активна. Є команда `management/commands/alerts.py`; у `compose.production.yaml` немає окремого планувальника, тож за самим репозиторієм не доведено автоматичний розклад на VPS.

**Пропозиція:** розділити «умова активна», «відповідальний прийняв», «роботу завершено», «причину усунено», «відкладено до». Фіксований/налаштований розклад з останнім успіхом/помилкою й доступною ручною командою. Поріг термінів/мінімумів — за правилами асортименту, а не лише 7 днів для всіх.

**Приймання:** натискання done не приховує невирішену нестачу; новий повтор умови відкриває новий цикл; збій планувальника видимий; ручний і автоматичний запуск не дублюють задачі. **Залежність:** B02, B13.

### B20 · P2 · Ідея → рішення → план → результат

**Доказ:** ідеї/задачі зберігаються у legacy `Document`, розділено spaces operations/development у `app/portal.js`; серверний облік не має сутності проекту/ініціативи з бюджетом, планом і виміряним результатом.

**Пропозиція:** для бізнес-ініціативи: проблема, гіпотеза, відповідальний, очікуваний ефект, оцінений бюджет, рішення, етапи/задачі, фактичні витрати і KPI. Пов’язати expense із проектом без зміни факту грошового руху; не дублювати поточні задачі облікового контролю в плані розвитку.

**Приймання:** з ідеї створюється проект із задачами і посиланням назад; план/факт відображаються окремо; завершення проекту містить виміряний результат; роль розвитку не обходить фінансові права. **Залежність:** B16, B18.

## 5. Інтеграції та перспектива росту

### B21 · P1 · Безпечний серверний імпорт замість серії незалежних записів

**Доказ:** `app/portal.js: buildPlan/applyImport` планує дані в браузері та послідовно додає/оновлює товари; збій дає частковий імпорт. У legacy `validate_product` немає повної перевірки cost/markup/price/manualPrice, що є у v1 `save_product`; шлях імпорту використовує `/api/docs`/`/api/products`. `import-preview` для облікових рядків уже перевіряє ID, кількість, ціну та дату, але не є імпортом каталогу.

**Пропозиція:** серверний preview каталогу: схема, нормалізовані значення, помилки з рядком/колонкою, створення/оновлення/конфлікти. Apply працює з перевіреним планом і revision; невеликий пакет атомарний, великий — фонові частини з журналом і ключами повтору. Не вважати рядок успішним, доки сервер не підтвердив запис.

**Приймання:** неправильний cost/manualPrice відхиляється однаково в React і імпорті; результат розрізняє створено/оновлено/пропущено/помилка; повтор пакета після обриву не створює дубль; записи конкурентного користувача не затерті. **Залежність:** B03/B06, єдиний валідатор каталогу.

### B22 · P2 · Google-таблиця: явні конфлікти й серверна координація

**Доказ:** `server/runtime.js` відхиляє MCP з текстом «Google connector is not configured on this server»; поточна VPS-версія не має Google OAuth цього застосунку. `app/portal.js: planSync` уже зупиняє дублікати/невідомі ID і зникнення відомого товару — ці захисти зберегти. При одночасній зміні поля в застосунку й таблиці обирається значення таблиці без окремого конфлікту. `gsSync` має лише локальне busy; записи таблиці/БД йдуть послідовно без спільної транзакції.

**Пропозиція:** серверний доступ із вузькими дозволами, план синхронізації/preview, третя база порівняння на сервері, конфлікт із обома значеннями, серверний lease, журнал фаз, retry/backoff і стабільні ключі створення. Видалення — явний tombstone/погоджений рядок, не відсутність у читанні. Поля, що є обліковими фактами, не імпортувати як довільні комірки каталогу.

**Приймання:** два пристрої не запускають дві конкурентні синхронізації; обрив після запису одного боку відновлюється без дублю; одночасне редагування ціни показує конфлікт; часткова відповідь Google не приховує товари. **Залежність:** доступ власника до потрібної таблиці, серверна OAuth-конфігурація, B06/B21; це не наявна інтеграція.

### B23 · P2 · ПРРО, банк і термінал через журнал інтеграції

**Доказ:** `post_voucher` лише вимагає непорожній fiscal_ref за налаштуванням; відсутній API фіскалізації/перевірки у провайдера. Рахунки bank/terminal є ручними CashEntry. Фіскальний номер не має перевірки унікальності/статусу провайдера.

**Пропозиція:** адаптер конкретного сервісу; стан операції «підготовлено → відправлено → підтверджено/помилка», зовнішній ID і ключ повтору, звірка після таймауту. Банківський імпорт: дедуплікація транзакцій, пропозиція відповідності боргу, ручне підтвердження невпізнаного платежу. Термінальні комісії окремими витратами.

**Приймання:** таймаут не створює другий чек/платіж; повернення має зовнішнє підтвердження; розходження управлінського продажу й провайдера видиме. **Залежність:** назва провайдера, документований API і дозволений доступ; до цього ручний номер має чесне позначення. Юридичні/фіскальні правила потребують окремої перевірки під конкретне використання.

### B24 · P2 · Кероване зростання API і проведень

**Стан 03.10.2026:** джерела/історія документів, касові зміни та табель мають серверну пагінацію; усі відкриті каси завантажуються окремо. Пошук платіжних джерел пакетно читає розрахунки: до 5 SQL у тесті 66 документів. Ledger/audit/debts також мають сторінки, пошук і totals; борги пакетно використовують obligation. Решта наведених нижче питань масштабування лишається відкритою.

**Доказ:** `/api/state` повертає весь legacy каталог; `server/runtime.js` запитує його кожні 5 секунд; `app/erp.js: load` знову завантажує всі товари. У `reporting.py` є запити на кожен рахунок/працівника/борговий документ, вкладені склад × товари; деталі рядків мають додаткові агрегати. `state` обрізає табель до 500 і зміни до 100, ledger до 500, історія клієнта в `customer-history` показує лише першу сторінку 30 документів. Глобальна блокада правильна для нинішнього обліку, але серіалізує також редагування каталогу/довідників.

**Пропозиція:** серверні пагінація/пошук і явні total/hasMore; зміни за revision/cursor замість постійної повної передачі; пакетні агрегати з виміром SQL/часу. Спочатку замірити сценарії 1/5/10 одночасних кас і великий каталог на ізольованій базі. Змінювати межі блокади лише після доведеного вузького місця, з однаковим порядком блокувань і тестами конкурентних багатоскладських/грошових рухів.

**Приймання:** історія й табель не ховають старі записи під виглядом повного списку; API має договірний ліміт; жоден тест навантаження не пише у production; нові блокади не дозволяють oversell або подвійне проведення. **Залежність:** версійний CRM OpenAPI; метрики продуктивності. React сам по собі не усуває ці серверні/мережеві межі.

### B25 · P2 · Звірка регістрів і готовність до відновлення

**Доказ:** `StockLot` зберігає поточний агрегат паралельно з `StockEntry`, гроші/борги обчислюються з рухів; `/health` перевіряє доступність `LedgerLock`, а не облікові рівності. Резервні процедури описані у [SERVER-DEPLOYMENT.md](SERVER-DEPLOYMENT.md), але цей аудит не перевіряв актуальність backup/restore на VPS.

**Пропозиція:** read-only команда звірки: суми складських рухів = StockLot quantity/value, підсумки документів = рядки + дозволені витрати, відсутні подвійні проведення, payroll calculation = accrued/total. Плановий звіт про відхилення, без автоматичного «виправлення» робочих даних. Окрема регулярна проба відновлення backup на ізольованій базі з тими самими рівностями.

**Приймання:** контрольна штучна неузгодженість в ізольованій базі дає точний ID/рівність; робоча перевірка не змінює облік; відновлений backup відкриває документи й проходить звірку. **Залежність:** B18, збережена схема/версія backup.

### B26 · P3 · Модуль CRM після надійного обліку

**Доказ:** `Counterparty` містить контакти/примітки, замовлення і документи; немає воронки, сегментів, дозволів на розсилки, балів чи правил лояльності. Це відповідає задокументованим межам, а не є несправністю наявного обліку.

**Пропозиція:** спочатку історія, середній чек, повторні покупки й прострочені оплати; потім сегменти/задачі контакту. Лояльність із журналом нарахування/списання/повернення балів і грошовою базою; канали повідомлень лише після вибору провайдера й правил згоди. Не нараховувати бонуси вдруге при retry.

**Приймання:** повернення коригує бали за вихідним продажем, повтор не дублює; контакт без дозволу не потрапляє у розсилку; особисті дані доступні за роллю. **Залежність:** B07/B18/B23 та конкретна програма лояльності.

## 6. Зв’язок бізнес-правил із зручністю React і CRM

### B27 · P1 · Бухгалтер має оплачувати доступний борг

**Стан 03.10.2026:** виправлено через scoped `/api/erp/references?purpose=payment` і пошук із пагінацією. Реальний ізольований бухгалтер оплачує надходження через UI; серверний тест проводить часткову оплату продажу. Права mutation receipt/sale та чужого магазину не надані. Також виправлено 500 у scoped report бухгалтера/менеджера.

**Доказ:** `app/erp.js: debtTable` показує кнопку оплати; `act('pay-debt')` спочатку GET-ить вихідний документ. У `views.py` GET `/api/erp/vouchers/:id` викликає `permission(user, v.kind)`; `ROLE_KINDS['accountant']` у `services.py` дозволяє payment, але не sale/receipt. Список пов’язаних документів у `voucherForm` теж використовує GET vouchers із фільтром типів, і сервер залишає тільки типи mutation-ролі. Бухгалтер бачить борги у report, але вихідний sale/receipt не проходить цей шлях вибору/відкриття.

**Пропозиція:** розділити право читання дозволених реквізитів вихідного документа і право його створення/редагування. Найменша межа — scoped endpoint «документи для оплати»: ID, тип, номер, магазин, контрагент, залишок, строк; без зайвих товарних/персональних даних. Деталі платежу й серверна перевірка боргу лишаються в payment-сервісі. Не додавати бухгалтеру mutation sale/receipt лише для розблокування селекту.

**Приймання:** бухгалтер магазину A оплачує надходження і борговий продаж A через UI та API; не створює/редагує/скасовує їх; не отримує документ B; часткова/повторна оплата сходиться з obligation. **Залежність:** B01/B02, окрема матриця read/write; цільовий сценарій бухгалтера.

### B28 · P1 · Серверний попередній розрахунок ціни до збереження

**Доказ:** `frontend/src/features/catalog/ProductEditor.tsx` показує `current.regularPrice`, тобто збережену ціну, і надсилає draft у save; окремого price-preview API у `catalog.py: handle_catalog` немає. При зміні закупівлі, націнки чи режиму користувач не отримує нового авторитетного розрахунку до запису. `regular_price` на сервері вже містить формулу й округлення; не копіювати її ще раз у браузері.

**Пропозиція:** read-only POST price-preview з нормалізованими cost/markup/manualPrice/price/promotionPrice та версією політики округлення; відповідь regularPrice, effectivePrice, валідність акції, попередження, використана формула. Дебаунс/AbortSignal, серверна помилка поруч із полем; застарілий запит не змінює новий preview.

**Приймання:** редагування націнки показує нову ціну до Save; preview і save для однакових входів/політики дають ті самі копійки; переключення ручної/розрахованої ціни не змішує стару ціну зі draft; preview не змінює priceAt чи документ. **Залежність:** B07/B14; versioned контракт.

### B29 · P2 · Конфлікт 409 із порівнянням змін

**Доказ:** `ProductEditor.tsx: reload` замінює draft актуальним товаром і просить повторити потрібні зміни. `Studio.tsx: reload` після підтвердження замінює чернетку серверним макетом; локальна чернетка при самому 409 зберігається. Це коректний захист перезапису, але вручну відновлювати багато правок незручно.

**Пропозиція:** тристороннє порівняння original/local/server з полями «лише моє», «лише сервер», «конфлікт». Автоматично переносити лише неперетинні правки; для перетинних — явний вибір. Спочатку зберігати/експортувати локальний draft, якщо користувач обирає повну заміну. Для макета diff по елементу/властивості, не сирий JSON.

**Приймання:** інший пристрій змінює name, локально змінюється pack → обидва збережені після узгодження; обидва змінюють ціну → обов’язковий вибір; save має нову revision і повторний конфлікт обробляється; немає прихованої бізнес-мутації під час перегляду diff. **Залежність:** B06, клієнтський baseline і серверний read актуальної версії.

### B30 · P2 · Керування довідниками: перейменування, об’єднання, архів

**Доказ:** `catalog_references.py` має get/create, детерміновані ID і дедуплікацію нормалізованих назв; товари зберігають текст значень, а `reference_items` підмішує legacy значення. Немає archive/merge/rename API. Просто видалити stored reference недостатньо: значення може з’явитись назад із товарів. Батько категорії зараз теж текст.

**Пропозиція:** стабільні reference ID в товарах з окремим display; legacy-адаптер на період міграції. Архів забороняє новий вибір, зберігає історію; merge перенаправляє використання й категорії транзакційно з preview кількості товарів. Перейменування групи не відриває категорії. Одиниці обліку підпорядкувати B03, не дозволяти довідникове merge змінити зміст залишків.

**Приймання:** архівований запис не повертається в active picker після повторного читання; існуючий товар показує своє збережене значення; merge не втрачає товари/історію; однакові категорії у різних групах не об’єднуються випадково. **Залежність:** план міграції каталогу/імпорту/Google, B03/B21.

### B31 · P1 · Єдиний безпечний формат CSV

**Доказ:** `frontend/src/features/labels/output.tsx: downloadCsv` і `app/portal.js: csv` лише беруть клітинки в подвійні лапки й екранують лапки; назва/категорія, що починається з `=`, `+`, `-`, `@`, лишається формульним текстом для табличного редактора. Це підтверджений форматний шлях, не твердження про виконання шкідливої формули у конкретній версії Excel/Sheets. `app/erp.js: download` уже додає апостроф для цих перших символів, але не нормалізує префікс керівних/пробільних символів; правило відрізняється між експортами.

**Пропозиція:** спільний CSV-serializer із явними типами numeric/text, коректними BOM/роздільником/лапками й нейтралізацією формульних текстових клітинок, зокрема після табуляції/переносу/початкових пробілів за визначеною політикою. Від’ємні облікові numeric значення мають лишатись числами; текст `-назва` — текстом. Для roundtrip-імпорту узгодити зняття лише доданого службового екранування.

**Приймання:** всі експорти перевірені на synthetic назвах `=1+1`, `+SUM(...)`, `@...`, `-товар`, таб/перенос, лапки/крапка з комою; гроші/від’ємні рухи зберігають точні числові значення; при відкритті у підтримуваному редакторі назви не стають формулами. **Залежність:** погоджений формат CSV; перевірка конкретних підтримуваних редакторів.

### B32 · P2 · PDF: прогрес, скасування і межа пам’яті

**Доказ:** `Studio.tsx: output` має загальний outputBusy і повторно перевіряє серверний знімок перед виводом — це зберегти. `output.tsx: exportPdf` створює raster 300 dpi, накопичує всі JPEG pages у пам’яті й після циклу збирає PDF; API не приймає AbortSignal/onProgress. Послідовний canvas.toBlob віддає виконання браузеру, але немає користувацького скасування між сторінками чи видимого номера сторінки. Навігаційний sequence guard після старту exportPdf не припиняє його внутрішній цикл.

**Пропозиція:** onProgress «сторінка N з M», cancel між сторінками та під час очікування шрифтів, гарантований cleanup hiddenHost. Показати до запуску число цінників/аркушів і оцінку обсягу; визначити практичну межу на синтетичних великих пакетах. Потім за виміряним ризиком — порційна генерація/worker або серверний експорт; не знижувати dpi/фізичний масштаб мовчки.

**Приймання:** cancel на сторінці 2 не завантажує частковий PDF, звільняє busy/host і дозволяє повтор; великий пакет показує прогрес і не блокує UI надовго; mm/pt та контроль обрізання збережені; повторна генерація не накопичує DOM/пам’ять. **Залежність:** існуючий PDF baseline і виміряні розміри пакета; пропорційний тест зміненого виводу.

### Мінімальні бізнес-рішення перед відповідними пакетами

1. Бонус: повернення після нарахування впливає на наступний бонус чи не впливає; кілька працівників отримують кожен відсоток усього виторгу чи частку фонду.
2. Знижка: межа касира, дозвіл менеджера, продаж нижче собівартості; ціна замовлення фіксується чи уточнюється перед видачею.
3. Каса: які готівкові рухи вимагають відкритої зміни; хто підтверджує нестачу/надлишок; інкасація між рахунками.
4. Запаси: асортимент по складах, мінімум/ціль, пріоритет резерву; кілька партій у накладній; одиниці фасовок.
5. Аналітика: дата сторнування/коригування, розподіл мережевих витрат, статті плану/факту.
6. Інтеграції: конкретні ПРРО/банк/термінал і джерело істини по полях Google-таблиці.

Це рішення для окремих пакетів; вони не блокують очевидні захисні виправлення B01/B02/B03 і доказове уточнення контрактів. Не вводити нові грошові правила мовчки під виглядом виправлення верстки.

## 8. Пропорційна перевірка

Дотримуватись [DEVELOPMENT-MODES.md](DEVELOPMENT-MODES.md): цільові тести зміненого правила, один наскрізний користувацький шлях, і збереження підтверджених результатів незмінених частин. Для доступу — позитивні/негативні API-сценарії; для revision — два клієнти; для проведень/резервів — відповідна конкурентність PostgreSQL; для грошей — точні Decimal і часткові повернення копійок. Перевірки запису — лише ізольована база.

Повна регресія має один явний запуск `npm run test:full` за окремим запитом. Для цієї документальної роботи вона не потрібна. Цей документ не стверджує, що перелічені пропозиції вже реалізовані, перевірені чи розгорнуті.
